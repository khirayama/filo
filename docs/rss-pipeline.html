Filo — フィード取得・更新と翻訳

RSS の取得・更新と、一覧タイトルの翻訳。この2つは互いに独立した仕組みで、 どちらもユーザーの明示操作で始まる。cron はコンテンツに触れない。

フィードを取得しても翻訳は始まらないし、翻訳しても取得は起きない。 取得が翻訳を自動で呼ぶことは意図的にしていない — 翻訳はプロバイダのリクエスト枠を消費し、 アカウント全体で直列にしか流せないため、取得のたびに走らせると枠を使い切ってしまう。

唯一の接点は、翻訳が対象にする記事を取得側が作っているという事実だけ。 起動が手動であることは方針として確定している（CONCEPT.md）。未確定なのは対象の絞り込みで、 現状は「対応5言語すべて × 全記事」を投入している。原文言語による絞り込みは B-7 のとおり構造上使えないため、別の切り口で解く。

A — フィード取得・更新
A-1
トリガー Manual
routes/subscriptions.ts · routes/status.ts

フィード取得を始める経路は3つだけで、すべてユーザーの操作。cron はフィードに触れず、失敗した account deletion job の再投入だけを担当する。

トリガーreason説明
API 新規購読 initial POST /subscriptions。購読作成直後の初回取得
API 手動更新 refresh POST /status/refresh（全購読） / POST /status/refresh/:feedId（個別）
API 初回失敗リトライ retry_initial POST /subscriptions/:id/retry-initial-fetch。paused でも受け付ける one-shot 復旧

全体更新（POST /status/refresh）が選ぶ対象

  1. クールダウンを過ぎた active フィードだけ
    status='active' かつ next_fetch_after <= now の購読フィードを最大200件。paused は対象外。
  2. スキップ数を返す
    クールダウンで除外した数を skipped として返すので、クライアントは「更新したのに何も起きない」を説明できる。
    { accepted: true, enqueued: 3, skipped: 27, queuedAt: "…" }
  3. force: true でクールダウン無視
    それでも paused フィードは対象にしない。個別更新（/refresh/:feedId）もクールダウンを見ない。
  4. ジョブ行を先に記録してから enqueue
    feed_jobs（user_id + feed_id で1行）に pending を書いてからキューへ。メッセージが失われても中断として画面に残り、ユーザーが再実行できる。
    await env.JOBS.send({ jobType: "fetch_feed", feedId, reason, attempt: 1 })
A-2
HTTP 取得 Queue
jobs/fetchFeed.ts · lib/net.ts

キュー filo-jobs（1バッチ5件、最大5回リトライ、失敗は60秒後に再投入）のコンシューマが1フィードずつ処理する。

  1. スキップ判定
    paused フィードの refresh は即 failed で終了。retry_initial だけは通し、成功すれば active に戻す。
  2. 条件付き GET
    保存済みの ETag / Last-Modified を送る。304 なら本文を読まずに完了し、記事の更新も走らない。
    headers: { "If-None-Match": etag, "If-Modified-Since": lastModified }
  3. SSRF ガードとリダイレクト
    private IP / localhost / link-local / metadata endpoint を拒否。リダイレクトは最大5ホップで、各ホップに同じ検査をかける。タイムアウト10秒、本文は5MBで打ち切り。
  4. 恒久リダイレクトだけ URL を追従
    301 のときだけ feeds.feed_url を新しい URL に移す。一時リダイレクトでは書き換えない。移設先が既存フィードと重複する場合は購読ごと統合する。
  5. https 死亡時の http プローブ
    https がネットワークレベルで死んでいるときだけ http を1回試す。ただし「http が https へ 301 している」ことを証明できた場合のみ転送先として信用し、平文のまま配信されている内容は拒否する。
A-3
パースと保存
lib/feed.ts · jobs/fetchFeed.ts
  1. XML パース
    RSS 2.0 / Atom / RDF を ParsedFeed に正規化。日付は ISO 8601 に揃え、解釈できない日付は null。
  2. フィードのメタ情報を更新
    title / site_url / description / favicon_url を反映。favicon の取得失敗は記事の取り込みを止めない。
  3. 重複排除キーを決める
    guid があればそれ、なければ正規化した URL、それも無ければ title + 公開日時 + 著者のハッシュ。(feed_id, dedupe_key) が記事の同一性。
    dedupe_key: guid:xxx | url:xxx | hash:sha256(title|published|author)
  4. upsert（1フィードあたり最大200件）
    既存記事はタイトル・本文・公開日時を更新（COALESCE で既存値を消さない）、新規記事は INSERT。挿入した記事の id を控えるが、翻訳の自動投入には使わない。
  5. 状態とログを記録
    feed_fetch_states に結果・ETag・次回取得時刻を、feed_fetch_logs に1回ぶんの実行記録を残す。feed_jobs は completed に確定。
A-4
次回取得タイミング Adaptive
lib/fetchSchedule.ts

next_fetch_after は「次にこのフィードを取りに行く価値が出る時刻」。更新は手動なので、これは自動巡回の間隔ではなく 更新ボタンの連打を無駄打ちにしないためのクールダウンとして働く。値はフィード自身の投稿ペースから決まる。

  1. 直近20件の投稿間隔の中央値をとる
    published_at を持つ記事の連続間隔の中央値。1つだけ空いた変則的な間隔に引きずられない。
  2. 沈黙が長ければその半分まで引き延ばす
    最終投稿からの経過時間の半分を下限として併用する。更新が途絶えたフィードを昔のペースで叩き続けないためで、同時に「毎朝まとめて10本」型のフィード（中央値1分）が終日1時間間隔で叩かれるのも防ぐ。
    interval = clamp( max( median(gaps), silence / 2 ), 1h, 24h )
  3. 1時間〜1日にクランプ
    下限1時間は、記事はセッション単位で読むものでライブ監視ではないため。上限1日は、長く止まっていたフィードが再開しても1日以内には拾えるようにするため。
  4. ペースが分からなければ従来値
    published_at を持つ記事が4件未満で中央値が信用できない場合だけ、success は1時間、304 は2時間にフォールバックする。

実測（購読130フィード）では投稿間隔の中央値は p10 = 17分、p25 = 2.7時間、p50 = 2.2日。 つまり大半のフィードは上限に張り付き、恩恵は「無駄な取得をしない」側に出る。ニュース系の速いフィードだけが下限の1時間に落ちる。

A-5
失敗と復旧
jobs/fetchFeed.ts · index.ts

失敗は状態として可視化し、ユーザーの操作で復旧する。自動で回収しにいく仕組みはない。

取得失敗
consecutive_failures を +1 し、バックオフ 1時間 → 6時間 → 1日。
3回連続で feeds.status = paused。
paused からの復帰
retry-initial-fetch の成功、または admin の PATCH /admin/feeds/:id。
復帰時に consecutive_failures = 0。
キュー / cron
ジョブ例外は60秒後にリトライ（最大5回）。
cron（毎時）は account deletion job の再投入のみ。

304 は失敗ではなく成功として扱い、consecutive_failures をリセットする。初回取得が失敗した購読は initial_fetch_status = failed になり、購読行から個別に再試行できる。

B — 翻訳
B-1
何を翻訳するか AI
lib/translate.ts
対象扱い理由
一覧の記事タイトル アプリが翻訳する。結果は全ユーザーで共有保存 一覧はスキャンするものなので、読めない言語のタイトルが並ぶと機能しない
記事本文 翻訳しない。各プラットフォーム / ブラウザの翻訳機能に委ねる 本文はコストが桁違いで、OS 側の翻訳が十分に使える
要約 生成しない MVP 対象外

翻訳先は ja / en / zh / ko / es の5言語。翻訳は記事に紐づく補足データとして article_listing_translations に共有保存し、ユーザーごとに複製しない。 音読キューで翻訳して聴きたい場合は、プラットフォームの翻訳を適用した後の可視コンテンツをキュー追加時に取り込む。

B-2
トリガーと投入 Manual
routes/status.ts

翻訳が始まるのはユーザーがボタンを押したときだけ。フィード取得は翻訳を呼ばない。

エンドポイント効果
POST /status/translate購読中の全フィードの不足ペアを投入
POST /status/translate/:feedId1フィードぶんだけ投入
POST /status/translate/discard待ち行列と失敗行を破棄（ready は残す）
POST /status/translate/:feedId/discard1フィードぶんだけ破棄
  1. 不足ペアを一括 INSERT
    対象フィードの全記事 × 対応5言語のうち、まだ行が無い組み合わせを status='pending' で作る。タイトルが空の記事は対象外。set-based SQL 1本なので記事数に関わらず即応答する。
  2. 失敗行を戻す
    error の行を pending・attempt_count = 0 に戻す。これが「再試行」で、専用の再試行 API は無い。
  3. drain を1メッセージ蹴る + watchdog を武装
    重複した drain メッセージは無害（仕事が無ければ1クエリで終了する）。
    await env.TRANSLATE_JOBS.send({ jobType: "translate_drain" })

既に ready のペアは再翻訳しない。強制再生成の API は用意していない。

B-3
台帳と状態
lib/translationCoverage.ts

翻訳は feed_jobs のようなジョブ行を持たない。article_listing_translations の行そのものが作業台帳で、 進捗・完了・失敗はすべてこの実データの集計（coverage）として表示する。 キューのメッセージが失われても、翻訳ボタンをもう一度押せば必ず回復するのはこの設計のため。

(記事 × 言語) の1ペアは、必ず次のどれか1つ。

missing — 行が無い（未リクエスト） queued — pending / processing_at null（順番待ち） processing — pending / processing_at あり（AI 応答待ち） ready — 完了 error — 3回失敗して確定
coverage の項目意味
articlesそのフィードの記事数
untranslatableタイトルが空で翻訳できない記事数
needed記事 × 対応5言語 の総ペア数
ready / failed完了 / 確定失敗
queued / processing順番待ち / AI 応答待ち（合計が pending）
missingneeded から上記すべてを引いた残り＝まだ要求されていないぶん
B-4
drain の動き Queue
jobs/translateDrain.ts

翻訳は専用キュー filo-translate で常に1本だけ走る（max_concurrency: 1）。 プロバイダのレート制限はアカウント全体で共有なので、並列に流しても互いを飢えさせるだけになる。

  1. 開始時に取り残しを掃除
    直列なので、drain 開始時に「AI 応答待ち」の行があるはずがない。前回クラッシュした drain が残した processing_at を消し、順番待ちに戻す。
  2. pending を200行スナップショット（新着優先）
    ORDER BY article_id DESC なので、新しい記事から訳される。取り切ったら次のスナップショットを取り直す。
  3. 記事単位にまとめて4件ずつのバッチに
    同じ記事の複数言語は1バッチに入れて、1リクエストで全対象言語を訳させる。バッチの対象言語は、そのバッチで実際に pending な言語の和集合だけ — 既に訳し終えた言語まで毎回生成させないため。
  4. 2バッチ同時にモデルへ
    デコードは重みのメモリ帯域が律速で重みは共有されるため、2本同時のほうが1本ずつより速い（実測 1タイトル約7.9秒 vs 約10秒）。4本同時は逆に遅くなる。ローカルサーバ側も lms load --parallel 2 で起動していないと2本目が待たされるだけになる。
  5. 投げる前に「翻訳中」を立てる
    モデル呼び出しは数十秒かかるので、先に processing_at を立ててステータス画面に「今これを翻訳中」を出す。レート制限で弾かれたバッチは印を外して順番待ちに戻す。
  6. 結果を書いてからペーシング
    同時実行したバッチの合算トークンから待ち時間を計算する。TRANSLATION_TOKENS_PER_MINUTE が未設定なら待たない（ローカルサーバはこちらが既定 — 枠ではなくマシンが律速なので、寝るのは純粋な無駄）。
  7. 60秒で切り上げて自分を再投入
    キュー呼び出しを長時間占有しないよう1回の drain は60秒予算。残りがあれば次の drain を delaySeconds 付きで送る。429 のときは Retry-After を30〜300秒にクランプ、進捗ゼロなら最低60秒空ける。

片方のバッチが 429 でも、同時に走ったもう片方の成功結果は必ず先に保存してから止まる（生成コストは既に払っているため）。

B-5
出力の検証
lib/translate.ts · lib/languages.ts

検証はモデルの品質を採点するものではなく、ユーザーに表示できない結果だけを弾くガードレール。 表示できる訳を言語判定の不確かさで捨てないことを優先する。

判定条件扱い
表示不可 空出力／原文の完全 echo（固有名詞として正当化できないもの） 同じ呼び出し内で最大2回まで修復を試み、直らなければ attempt_count + 1 で pending に留める
警告 文字種の混在、固有名詞・URL・型番の残存、短いタイトル、言語ヒューリスティックが不確か ready として保存する。警告はワーカーのログにだけ残り、失敗数や error_message には出さない
採用 上記以外 ready

技術系の見出しは製品名・バージョン・数字が大半を占めるので、正しい翻訳でも対象言語の文字がほとんど残らないことがある （「2026-07-05의 JS: Deno 2.9, Vite 8.1, ES2026」はハングル1文字でも正しい韓国語）。 ここで捨てるとタイトルは翻訳なしになり、残せばユーザーは一目で変だと分かる。だから残す側に倒している。

attempt_count が3に達したペアが error として確定する。

B-6
watchdog
jobs/translationWatchdogPolicy.ts · jobs/translationWatchdog.ts

drain は「自分の続きを自分でキューに入れる」1本の鎖で進む。鎖が切れる（例外でのクラッシュ、ローカル wrangler dev の再起動でインメモリキューが消える）と、待ち行列が残ったまま誰も再開しない。 その保険が Durable Object の watchdog。

  1. drain を蹴るたびに武装する
    アラームは永続化されるので、プロセスが落ちても監視が続く。
  2. 60秒ごとに様子を見る
    pending が0なら何もせず眠る（次に武装されるまで）。
  3. 180秒動きが無ければ drain を再投入
    健全な drain はバッチごとに行を更新するので数十秒おきに動きがある。ペーシング待ちの drain を死んだと誤認しないよう、drain の無進捗バックオフ（約60秒）より十分に長くとってある。
B-7
原文言語の扱い（設計上の制約）
lib/translate.ts · lib/languages.ts

原文言語は事前に判定していない。 翻訳リクエストにソース言語を渡さず、モデルがタイトルごとに source_lang を返し、それを articles.source_language に保存する。 複数言語混在は mixed、判定不能は und のまま保持する。

つまり 原文言語は翻訳の入力ではなく出力。ここから2つの帰結がある。

  1. 「原文が読める言語なら翻訳しない」は実装できない
    翻訳しないと原文言語が分からないので、翻訳の起動条件に原文言語を使うと鶏と卵になる。原文と同じ言語への翻訳はモデルが原文をそのまま返し、それを正当な結果として受理する。
  2. 言語判定に依存する最適化は採用しない
    記事単位の事前判定は不安定で、フィード単位の推定も混在フィード（ポッドキャスト、ブックマーク集、語学系）では外れる。取得と翻訳を分離したまま、別の仕組みで解く方針。

表示側（一覧）はこの保存済み原文言語を見て、ユーザーの readableLanguages に含まれない場合にだけ翻訳タイトルを出す。 裏返すと、まだ一度も翻訳されていない記事は原文言語が未確定なので、翻訳中バッジも出ない。

C — 周辺
C-1
本文抽出 Manual
jobs/extractContent.ts · routes/content.ts

本文はリーディングパート（音読キュー）のためだけに扱う。一覧・詳細では本文を扱わず、要約も作らない。 取得や翻訳とは独立していて、記事を開く / 音読キューに入れるときに POST /articles/:id/content で要求される。

  1. RSS 本文を優先
    content:encoded / summary で足りればそれを使い、足りないときだけ canonical_url の HTML を取りに行って本文を抽出する。
  2. article_contents に共有保存
    text / html を保存。失敗は status='error' として残り、再要求できる。行の存在自体が「抽出を要求済み」を意味するので、抽出以外の用途でこの行を作ってはいけない。
